# Engine reference

[← Back to the overview](../README.md)

Secures a GitHub organization from one config file (`github.json`, kept in a repository of the organization). From it, the engine:

- **applies organization settings** GitHub lets an API change: the base permission of members and what members may create, whether deploy keys may be used, and the public contact email;
- **restricts GitHub Actions**: which actions may run, SHA pinning, the default `GITHUB_TOKEN` permissions, self-hosted runners, workflows from forks, how long artifacts and logs are kept;
- **limits the Copilot cloud agent**: which repositories it may work in;
- **keeps the budgets**: a monthly limit per paid product, with the owners as the only recipients of the alerts;
- **keeps the Copilot seats**: buys a seat for every login and team member of the config without one, and names the cost in the plan; a seat outside the config is a [warning](#warnings);
- **keeps a code security configuration**: the free security features (dependency graph, Dependabot alerts and security updates, private vulnerability reporting, which works on public repositories), the default for new repositories and attached to every repository without a configuration;
- **checks the settings GitHub lets an owner change only in the web UI** (the two-factor requirement, a verified domain, and whether members may delete repositories, change their visibility or invite outside collaborators) and reports a mismatch as a [warning](#warnings).
- **keeps one organization ruleset** on the default branch of every repository, new ones included: no direct push, no deletion or force push, a pull request with an approval of another person, merge commits only, the teams of `ruleset.rules.pullRequest.requiredReviewers` (such as `platform-admins`) approving changes to workflows, and the central workflows of `ruleset.rules.workflows` (such as [`examples/org-checks.yml`](examples/org-checks.yml), run from the `.github` repository) required on every pull request. With `ruleset.rules.copilotCodeReview.enabled`, Copilot reviews every pull request, and its comments, like any review thread, must be resolved before the merge. The organization admin can merge without the approval (GitHub records it), never push;
- **compares the inventory** with the config on every run: owners, installed GitHub Apps (with their repository access and permissions), organization webhooks (by host, and whether each uses `https`, verifies SSL and has a secret) and outside collaborators; every difference is a [warning](#warnings), and so are a single owner and every pending invitation to the organization or one of its repositories.

It changes only the fields in the config, never changes members, outside collaborators, invitations, teams, Apps or webhooks (it only reads them), changes repositories only by attaching the code security configuration to those without one (never switching a configuration), never cancels a Copilot seat, and never deletes anything.

Design and reasoning: the [founding decision](../docs/decisions/2026-11-13-github-org-bootstrap-design.md).

## Requirements

PowerShell 7.6 and the [GitHub CLI](https://cli.github.com/) 2.48.0 or later, signed in as an owner of the organization (open a new terminal after installing, otherwise `gh` is not on `PATH` yet):

```powershell
winget install --id GitHub.cli -e
gh auth login
```

The run needs the `admin:org` and `admin:org_hook` scopes (GitHub has no read-only scope for organization webhooks). With them, the gh token on the operator machine is nearly an owner: stolen, it can change every setting of the organization and push to `main` of any repository, and so to whatever its workflows deploy. Grant them only for a run and remove them afterwards; the engine prints the removal command at the end of every run, also after an error or an answer of `n`:

```powershell
gh auth refresh -h github.com -s admin:org,admin:org_hook   # before the run
gh auth refresh -h github.com -r admin:org,admin:org_hook   # after the run
```

Before the first run with `sha_pinning_required: true`, every workflow of every repository in the organization must reference actions by full commit SHA, otherwise it fails from then on:

```yaml
- uses: actions/checkout@<40-character commit SHA> # v5.0.0
```

Look up a tag's SHA with `gh api repos/<owner>/<action>/commits/<tag> --jq .sha`. A `.github/dependabot.yml` with the `github-actions` ecosystem keeps the SHAs and their comments up to date; this repository has one.

The `ruleset` section is required, so before the first run do the [manual setup](#manual-setup): the `.github` repository with the central workflow and the reviewer team the config names (`platform-admins` below, `example-admins` in the example). The plan stops without them, since the ruleset would block every pull request in the organization.

## Operator permissions

Owner of the organization.

## Usage

```powershell
./engine/bootstrap.ps1 -ConfigPath ./github.json -WhatIf     # show the plan and warnings, change nothing
./engine/bootstrap.ps1 -ConfigPath ./github.json             # show the plan, confirm and apply
./engine/bootstrap.ps1 -ConfigPath ./github.json -WhatIf -ManualChecklist   # also list the settings only a person can check
./engine/bootstrap.ps1 -ConfigPath ./github.json -WhatIf -PageWalk          # walk the settings pages one at a time
./engine/bootstrap.ps1 -ConfigPath ./github.json -ValidateOnly              # check the config only: no gh, no sign-in, no GitHub call
```

Set the pages by hand with `-WhatIf -PageWalk`: it shows the settings pages one at a time in the order of the settings menu, opens each page that needs a person in the browser and waits for Enter (`q` ends the walk; the run then goes on to the confirmation). On each page it lists every row of the config top to bottom as the page shows it, under the group headings of the page, with a mark:

| Mark | Meaning |
| --- | --- |
| `[ok]` | the value GitHub returned equals the config |
| `[apply]` | the engine changes it when the plan is confirmed |
| `[DIFF]` | differs and the engine does not change it this run: set it on the page (now X, expected Y) |
| `[?]` | the run could not read it, with the reason |
| `[n/a]` | does not apply or was not read this run, with the reason |
| `[set]` | only a person can check it: set or confirm the expected value |

The marks show the state the run read, at the time on the walk's first line, not the page as it is when you look at it: a change made during the walk shows on the next run. Enter only moves to the next page: it confirms nothing, a `[set]` row stays `[set]`, and the walk records nothing. A page with nothing to do takes one line and no stop; the pages of the ruleset, code security, budgets, Copilot seats, webhooks and GitHub Apps show their planned actions and warnings instead of rows, and a last block shows what belongs to no settings page. Without an interactive host (CI, `-NonInteractive`) it prints every page and never stops. Each page header names the day its UI names and order were read (`UI read <date>`); a control in another place or wording than the walk shows is a pull request that fixes the rows and `Order` of the page and its `ReviewedOn`.

A setting with no API read (a `manual` row) is never read or written by the engine, even where GitHub has a write for it. A run that has such rows ends its report with one line, `Manual: <n> settings have no API read; this run did not check them`, and `-ManualChecklist` lists them after it, by settings page: the address, the group and control to look at, the value the config expects (and the recommendation where it differs) and why; without such rows it prints `No settings need a manual check.` The list comes before the confirmation, so it also prints with `-WhatIf`, with nothing to change and with `-Force`. A closed review issue confirms that the pages were walked against the checklist on that date, never the value of a single setting: a `manual` setting is "not checked by this run" on every run, however recent the review.

### Manual setup

Once, before the first run with the `ruleset` section; the engine never creates repositories, teams or members. The owner does:

1. Create the private repository `.github` in the organization, with the central workflow `.github/workflows/org-checks.yml` (a copy of [`examples/org-checks.yml`](examples/org-checks.yml), by a pull request or a first commit) and Dependabot for its actions. Open its *Settings → Actions → General*, under *Access* select "Accessible from repositories in the organization", and save. Without that, the other repositories cannot run its workflow.
2. Create the reviewer team of `ruleset.rules.pullRequest.requiredReviewers` (here `platform-admins`), add yourself, and assign it the organization role "All-repository write" (`all_repo_write`) under *Organization settings → Organization roles → Role assignments*. GitHub counts a team's approval only where the team has write access, and the role covers new repositories too.
3. Add a `CODEOWNERS` file to the repository of the config and to every repository whose workflows deploy, owning at least itself: `* @<org>/platform-admins` and `/.github/CODEOWNERS @<org>/platform-admins`. Code owner review has no effect in a repository without one, so a repository opts in by having the file.
4. Turn off squash and rebase merging in both repositories (*Settings → General → Pull Requests*). The ruleset allows only merge commits but does not change the repository settings, which still offer the other methods until turned off.
5. Put the commit SHA of `.github/workflows/org-checks.yml` (the merge commit of the pull request that added it) in `ruleset.rules.workflows[].sha` of `github.json`, run `./engine/bootstrap.ps1 -ConfigPath ./github.json -WhatIf`, then the real run.

The reference copy of a required workflow is the file of the same name beside the config (such as [`examples/org-checks.yml`](examples/org-checks.yml), kept as `org-checks.yml` beside `github.json`); every run compares the workflow at the configured commit with it. A workflow without such a file is not compared; the run still checks that its repository and file exist and that it can run. A change to the central checks is a pull request to the reference copy beside `github.json` first, then the copy to `.github` by a pull request there, then the new merge commit in `github.json` and a run of the engine; a recurring reminder in the config repository helps to keep them in line. Write access to `.github` alone cannot swap a check, since the ruleset pins the commit.

### Copilot code review

Before `ruleset.rules.copilotCodeReview.enabled` has an effect: GitHub accepts the rule without a Copilot plan, but no pull request gets a review, and the engine [warns](#warnings) on every run.

1. Buy **Copilot Business** on `access` ("Enable GitHub Copilot"; billed per assigned seat and month, cancelled by removing every seat) and assign the first seat there: choose selected members, since every seat is paid, and GitHub has no API for this choice. Everyone else who opens pull requests goes into [`copilotSeats`](#config), and the engine buys their seats. A review is charged in AI credits; on private repositories it also uses Actions minutes.
2. Raise `ai_credits` in [`budgets`](#config) and run the engine, and set *Choose how members with a Copilot license are billed* to the organization (`copilot/policies`, step 3). Billed to the member, a review fails with "insufficient remaining quota", whatever the budget says.
3. Set the Copilot pages as `./engine/bootstrap.ps1 -ConfigPath ./github.json -WhatIf -ManualChecklist` lists them (the groups, controls and expected values, with the reason of each). The engine reads and checks what GitHub's REST API shows (the code review policy, the review effort and runner, the policies of `copilot/billing`; see [`settings.md`](settings.md)) and warns when it differs; the rest only the page shows. All but `policies`, which appears with the purchase, can be set before it.

Copilot follows `.github/copilot-instructions.md` of each repository. It reads the instructions from the branch of the pull request, so a pull request could soften them for its own review: `requiredReviewers` covers every file it reads them from.

A review only comments and suggests fixes; it never approves or requests changes. What blocks the merge is `required_review_thread_resolution`: each comment is a thread someone resolves, fixed or answered. A pull request that Copilot did not review (no seat, budget used up, an outage, merged before the review arrived) merges as before.

### Settings without an API

Some settings only a page shows. They are rows of the config like any other, with mode `manual` (their sections and expected values in [Config](#config)), so the schema, the recommendations and `exceptions` cover them; the run never reads them and says so in one line: `Manual: <n> settings have no API read; this run did not check them.` `./engine/bootstrap.ps1 -ConfigPath ./github.json -WhatIf -ManualChecklist` lists them by page, in the order of the page, with the address, the group and control, the expected value, the recommendation where the config differs, and why; it changes nothing else in the run, with or without `-WhatIf`. `-PageWalk` shows them on their pages among the other rows ([Usage](#usage)).

[`settings.md`](settings.md) is the generated reference of every settings page of the organization: for each one its rows (applied, checked or manual) or the reason the engine leaves it alone, and every API endpoint with its fields. The recurring "Settings pages review" of this repository walks the pages against it every 90 days and goes through the checklist; a closed review records that walk, never the value of a single setting, so a manual setting stays "not checked by this run" on every run. A setting that changes later is in the [audit log](#manual-verification).

Account of every owner, under `https://github.com/settings/`: `security` (two passkeys or security keys, one kept apart; recovery codes stored offline; a linked Google or Apple sign-in only if that account is protected as well; no verified email that is no longer used), `sessions`, `keys`, `applications` (authorized OAuth Apps and GitHub Apps; revoke what is no longer used), `tokens` (classic) and `personal-access-tokens` (fine-grained): nothing unknown. An owner account is the whole perimeter: it can push to `main` of the platform repository and change every setting above.

**Recovery:** add a second owner, or store the owner's two-factor recovery codes offline. An organization whose only owner loses their second factor cannot be recovered.

## Config

[`examples/github.json`](examples/github.json) is a complete example (placeholders for the organization, its people and its workflow commit), validated by the tests of the engine. Field names are GitHub's own, see the REST API reference for [organizations](https://docs.github.com/rest/orgs/orgs#update-an-organization) and [Actions permissions](https://docs.github.com/rest/actions/permissions). Every section and field is required and an unknown one is a config error; [`github.schema.json`](github.schema.json) describes every field with its recommended value and the reason, and VS Code shows them on hover and completes the fields. [`settings.md`](settings.md) is the generated reference of every settings page and API endpoint the engine knows, with the rows that cover them.

- `configVersion`: the config format the file is written in, `major.minor` (now `1.0`). The engine reads its own major version up to its own minor version and stops before any GitHub call otherwise. A new major means the config needs an edit (a field added, removed, renamed or moved); raise the value with that edit.
- `inventory`: what the organization is expected to have; compared on every run, never changed. An App entry is written as its installation shows it: `{ "slug": "claude", "repositorySelection": "selected", "permissions": { "contents": "write", "metadata": "read" } }`. `[]` for none.
- Every field has a mode, listed per page in [`settings.md`](settings.md): `apply` (the engine sets it), `check` (the engine reads it and warns when it differs: GitHub has no API to change it, or the engine does not apply it yet) and `manual` (only the page shows it, see [Settings without an API](#settings-without-an-api)). Write the value the organization should have for each; `settings.members_can_invite_outside_collaborators` can only be restricted on GitHub Enterprise Cloud, so on other plans it is `true` with an exception.
- `settings`, `actions` (and its subsections) and `copilotCloudAgent` each follow one API endpoint and hold only its fields. Sections by page or subject hold the other checked settings and the manual ones: `authenticationSecurity`, `memberPrivileges`, `repositoryDefaults`, `projects`, `copilot` (`policies`, `models`, `codeReview`, `internetAccess`, `runnerType`, `automations`, `partnerAgents`), `personalAccessTokens`, `oauthApps`, `codespaces`, `packages`, `discussions`, `interactionLimits`, `immutableReleases`, `dependabot`, `advancedSecurity`, `actions.oidc` and `actions.cache`. A manual value is the option of the page in lower case (`restrict`, `disabled_everywhere`); a checked one is the value of GitHub's API (`block`, `unconfigured`). Without a Copilot plan the Copilot settings that the API reads are one line `<n> checked settings are not checked`, not a warning each.
- `actions.selected` is an object when `allowed_actions` is `selected`, `null` otherwise. Add an action to `patterns_allowed` and re-run before a workflow starts using it.
- `copilotCloudAgent`: `enabled_repositories` is the *Repository access* of the cloud agent, `none` while it is not used. With `selected`, the repositories are chosen on the page `https://github.com/organizations/<org>/settings/copilot/cloud`: the engine does not manage that list. The endpoint is in public preview in GitHub's REST API.
- `codeSecurity`: attached to repositories without a configuration (archived ones excluded); others are left alone. The repositories of organization and built-in GitHub configurations are read from each configuration's list, so a run makes a few requests whatever the number of repositories; only a repository without a configuration, or with an enterprise one, is read on its own. `name` matches the organization configuration exactly, case included. `description` may be `null`.
- `ruleset`: the one organization ruleset the engine creates and then replaces whole whenever a field differs, so a change made in the web UI is planned back; a condition or rule parameter the engine does not model is a [warning](#warnings) instead. It always targets the default branch of every repository (fixed, not configurable). `name` matches the ruleset exactly, case included; `enforcement` is `active` or `disabled` (`evaluate` needs Enterprise); `bypass.organizationAdmin` is `pull_request` (an organization admin merges a pull request without the approvals, recorded by GitHub, never pushes) or `none`; `rules.deletion` and `rules.non_fast_forward` block deleting and force-pushing the branch. `rules.pullRequest` holds the pull request parameters (`required_approving_review_count` 0 to 10, the dismissal, last push, code owner, thread resolution and unattributed-change switches, `allowed_merge_methods`) and `requiredReviewers`: per team slug, `minimum_approvals` and `file_patterns` of the files whose changes that team must approve. `rules.workflows` lists the required workflows as `{repository, path, sha}`: the repository of the organization (the `.github` repository), the file under `.github/workflows/` and the full 40-character commit it is read at, which only a run of the engine changes. At least one workflow is required, and some `requiredReviewers` entry with at least one approval must cover `.github/workflows/**`, or anyone with write access and one approval changes the workflows that deploy with the credentials of the repository: without one the run stops unless an exception on `ruleset.rules.pullRequest.requiredReviewers` covers it. `rules.copilotCodeReview.enabled` asks Copilot to review every pull request (see [Copilot code review](#copilot-code-review)); with it, `review_on_push` reviews each new push too and `review_draft_pull_requests` drafts as well. `enabled: false` leaves the rule out, a recommendation warning like any other until an exception covers it. Other rulesets of the organization are never changed or deleted.
- `budgets`: one entry per budget of the organization, in the names of GitHub's API; a paid product without a budget has no limit. `budget_type` is `BundlePricing` for `ai_credits`, `ProductPricing` for a product, `SkuPricing` for a single SKU; the ids are in [Product and SKU names](https://docs.github.com/en/billing/reference/product-and-sku-names). `budget_amount` is whole dollars a month, or the number of licenses for `ghas_*_licenses`. Code Security and Secret Protection are SKUs because the stop works there; it blocks new enablement, it does not turn them off where they are on. Alerts are always on and go to `inventory.owners` only: a recipient added on the page is planned away. Raise `ai_credits` before buying Copilot.
- `copilotSeats`: who holds a Copilot seat, every seat being paid ($19 a month on Copilot Business, $39 on Enterprise). `selected_usernames` are logins with a seat of their own, `selected_teams` team slugs whose members hold one; `[]` for none. A login or team member without a seat is bought, the cost named in the plan, once seat management is "selected members". GitHub does not list the teams it was given, only the seats, so a team is compared through its members: a team with no one left to buy for is not planned, and an empty one gets its seats on the first run after it has members. A seat is never cancelled, so removing a login here only turns its seat into a warning. The seat endpoints are in public preview in GitHub's REST API.
- **Recommendations.** Most settings have a recommended value; the others say in the schema (hover in VS Code) why they have none: project data, or a decision of the owner. A config value that differs is a warning on every run, unless `exceptions` covers it: `field` (the path, such as `settings.members_can_invite_outside_collaborators`), `category` (`waiver`: the risk is accepted; `mitigated`: another control covers it), `reason`, `expiresOn` (`yyyy-MM-dd`, at most one year ahead) and `reference` (an `https://` link or `null`). `[]` for none.

## Warnings

Printed with the plan, also with `-WhatIf`; they never block the run.

- **Setting differs from its recommendation.** Change the config, or add an entry to `exceptions` with the reason and a date to look at it again (see [Config](#config)). The warning names the recommended value and why. An exception in force is not a warning: a `Waived until ...` line after the warnings keeps it visible, with `(expires in N days)` in its last 30 days.
- **Exception expired.** Renew the exception with a new date, or change the value. The deviation is a warning again.
- **Exception not needed.** Remove the exception. The value is the recommended one, for example after a plan change.
- **A checked setting differs.** Change it on the settings page the warning names (it also names the group on it and the checkbox to select or clear) and save; the next run shows no warning. For `is_verified`, add the domain on the page the warning names, create the DNS TXT record GitHub shows and verify it; DNS can take a while to propagate. For a setting GitHub has no API to change, the warning says so; for one the API could change, it says that this tool does not apply it yet: change it on the page either way.
- **Setting not observed.** Check the setting by hand on the page the warning names; the run could not read its value, so it compared nothing. The reason says why: `answered 401` means the gh token is missing, expired or revoked (`gh auth login`); `answered 403` means the account may not read it (run `gh auth refresh -h github.com -s admin:org,admin:org_hook`); `answered without the field`, `404` or a plan restriction mean GitHub did not return the value, so only the page shows it; `failed` is a technical error, re-run. A line `<n> checked settings are not checked: <reason>` means the feature does not exist for the organization (for example no Copilot plan), which is not an error.
- **GitHub returned a field the engine does not know.** In a pull request, add a row for the field, or list it under `Fields` of the GET in [`api-endpoints.psd1`](api-endpoints.psd1) with the reason the engine leaves it alone. GitHub added a field to an answer the engine reads, possibly a new setting nobody has looked at; the warning names the fields, never their values. For a section the engine sets with a PUT (everything but the organization settings) it plans no change to that section until then, since a PUT replaces the whole section and could reset the field (the allowed-actions list too, while allowed_actions is not `selected` yet); re-run after the pull request is merged. Only the endpoints of the settings sections are checked.
- **SHA pinning becomes required.** Pin every workflow first (see [Requirements](#requirements)). From then on every workflow that references an action by tag or branch fails.
- **Repository with another code security configuration.** Apply the configured one on the page the warning names if you want it. The engine does not switch it.
- **Code security attachment failed.** Check the configuration page named in the warning, then re-run.
- **Code security configuration not in effect on a repository.** Apply the configuration to the repository again on the page the warning names. The repository is still associated with the configuration, but GitHub reports a [status](https://docs.github.com/en/code-security/reference/security-at-scale/configuration-statuses) such as `removed` (a repository admin changed a setting it controls, possible only while `enforcement` is `unenforced`), `removed_by_enterprise` or `detached`; the engine does not re-attach it.
- **Repository left out of the run.** Re-run; a warning that stays means the account lacks access to the repository. Its code security configuration could not be read because GitHub answered 404: it was deleted, renamed or transferred between the repository list and its own read, or the gh account cannot see it.
- **A requiredReviewers team does not exist.** Create the team (see [Manual setup](#manual-setup)), or remove it from the config. The ruleset cannot name a team that does not exist, so the engine plans no change to it, a create included, until it does.
- **A requiredReviewers team has no write access to every repository.** Assign the team the organization role "All-repository write" on the organization's role assignments page the warning names. Its approvals do not count otherwise, so pull requests that change its file patterns wait for an organization admin.
- **Copilot code review without a Copilot plan or seat.** Buy Copilot Business and assign seats (see [Copilot code review](#copilot-code-review)), or set `ruleset.rules.copilotCodeReview.enabled` to `false`. The engine still sets the rule, but no pull request gets a review without a plan, and without seats only authors with a license of their own do; the merge is not blocked either way.
- **The ruleset has a field the engine does not model** (`conditions.<name>`, `conditions.<name>.<field>` or `rules.<type>.<parameter>`). Review it on the page the warning names and remove it there unless it is wanted; if GitHub added it, or it should stay, add it to the engine (a config row and the comparison). The engine neither compares nor sets such a field and plans no change for it: a parameter GitHub adds with a default would otherwise plan an update on every run. An extra condition can narrow which repositories the ruleset applies to, an extra parameter can loosen a rule. Whether a later update of the ruleset drops the field is not verified.
- **Another ruleset in the organization.** Review it on the page the warning names; the engine never changes or deletes it. GitHub combines the rules of every ruleset that applies and the strictest wins, so another ruleset can add rules but not weaken this one.
- **The central workflow differs from `org-checks.yml` beside the config.** Copy the reference copy beside the config into the `.github` repository by a pull request, then put the merge commit of that pull request in `ruleset.rules.workflows`. The content is compared ignoring line endings. The file at the configured commit is what GitHub runs, so a difference means the organization runs checks other than the reviewed copy, or the reference copy has not reached `.github` yet.
- **Single owner.** Add a second owner, and keep the recovery codes offline. Nobody can recover an organization whose only owner loses their second factor. Shown on every run until there are two owners.
- **Owner, App or webhook not in the inventory, or listed but gone.** If you made the change, update `inventory`; if not, act on the page the warning names and review the audit log. Unexpected owners, Apps and webhooks are how access is kept after a compromise; a deleted audit webhook can hide one. A webhook is shown as `scheme://host/...`: the rest of its URL can be a secret.
- **Webhook not secure.** Fix it on the page the warning names: an `https` URL, SSL verification enabled, a secret that the receiver checks. Shown for every organization webhook, listed in the inventory or not, whose URL is not `https` (the events travel in clear text), whose SSL verification is off (anyone in between can read and answer the deliveries) or that has no secret (the receiver cannot check `X-Hub-Signature-256` and accepts forged deliveries); one warning names every problem of the webhook. The engine only reads whether a secret is set, never the secret ([CIS Software Supply Chain Security Guide](https://www.cisecurity.org/benchmark/software-supply-chain-security) 4.3.4, [OpenSSF Scorecard Webhooks](https://github.com/ossf/scorecard/blob/main/docs/checks.md#webhooks)).
- **App differs from the inventory.** If you made the change, update `inventory`; if not, review its access on the installations page the warning names and the audit log. Its repository access or permissions changed (for example `selected -> all`, or a new `workflows: write`); the warning names every difference.
- **Outside collaborator not in the inventory, or listed but gone.** If they are listed but gone, update `inventory`. If they are not listed and you added them, update `inventory`; if not, remove them on the page the warning names. An outside collaborator reaches repositories without being a member, so the base permission does not cover them and nobody reviews them with the members.
- **SSL verification of a webhook not reported.** Check the webhook on the page the warning names and enable SSL verification if it is off. Shown for an `https` webhook when GitHub's answer does not say whether verification is on, so the engine does not count it as verified.
- **Budget not in the config.** Add it to `budgets` if it is expected, otherwise delete it on the page the warning names: the engine never deletes a budget.
- **`ai_credits` stopped at 0 with a Copilot plan.** Raise `budget_amount` in `budgets`. A review is charged in AI credits, so reviews stop once the included credits are used up.
- **Copilot seat not in the config.** Add the login or team to `copilotSeats` if it is expected, otherwise remove the seat on the page the warning names: the engine never cancels a seat. A seat given by mistake is paid every month, so every seat is listed. A seat already being cancelled is not shown.
- **Copilot seat of the config being cancelled.** Assign it again on the page the warning names, or remove it from `copilotSeats`. Until the date in the warning the login still holds the seat, so the engine plans nothing.
- **Copilot seats managed other than as selected members.** Choose selected members on the page the warning names. GitHub rejects a seat otherwise, so the engine plans none, and `assign_all` pays a seat for every member.
- **`copilotSeats` without a Copilot plan.** Buy Copilot Business and assign the first seat on the page the warning names (see [Copilot code review](#copilot-code-review)), or empty `copilotSeats`. GitHub has no API for this first step, so the engine buys no seat until then.
- **A team of `copilotSeats` does not exist.** Create the team, or remove it from the config. It gets no seats until then.
- **Pending invitation.** Cancel an unexpected one on the page the warning names and review the audit log; an expected one stops showing once it is accepted. An invitation to the organization is access waiting to be accepted, possibly by the wrong account; the warning names the invitee (login or email), the role, who sent it and when.
- **Pending or expired repository invitation.** Cancel an unexpected one on the repository's *Collaborators and teams* page the warning names; for a pending one, also review the audit log. An outside collaborator is invited to a single repository, and GitHub lists those invitations only per repository, so the engine reads every repository, archived ones included (accepting still gives read access to the code). The warning names the invitee, the repository, the access, who sent it and when. An expired invitation can no longer be accepted, but an administrator of the repository can resend it, so it is shown too, marked expired, until it is cancelled. GitHub Team cannot stop repository administrators from inviting outside collaborators (only Enterprise Cloud can), so this warning is the control.
- **Invitations of a repository could not be read.** Re-run; if the warning stays, check on the repository's page that it exists and that the gh account can see it. GitHub answered 404 for a repository in the list: it was deleted, renamed or transferred during the run, or the account cannot see it, so its pending invitations are not in this run.

## Troubleshooting

- **`Cannot read the Actions settings of '<org>'` or `Cannot read the webhooks of '<org>'`:** gh lacks a scope, usually because it was removed after the previous run; run `gh auth refresh -h github.com -s admin:org,admin:org_hook` and re-run.
- **`run.ps1` stops with `... .engine has local changes, so it is not the pinned engine`:** remove `.engine/` (copy out what you want to keep first) and run `./run.ps1` again, which checks out the pinned commit afresh. The wrapper runs only the engine as released and never deletes a changed file itself, also when `engine.psd1` pins another release; a change to the engine goes into this repository instead.
- **`... differs from codeSecurity.name ... only in case`:** GitHub has the configuration under another spelling, and an update never renames it; use its spelling in `codeSecurity.name`, or rename it on the page the error names.
- **`'<name>' is the name of a built-in GitHub (or an enterprise) code security configuration`:** configuration names are unique across the organization; choose another `codeSecurity.name`.
- **`... differs from ruleset.name ... only in case`:** GitHub has the ruleset under another spelling, and an update never renames it; use its spelling in `ruleset.name`, or rename it on the page the error names.
- **The run stops with a ruleset precondition error** (`... has no such repository`, `... has no .github/workflows/org-checks.yml at commit ...`, `... does not share its workflows with the organization`, `... cannot run in the ... repositories`): follow the instruction in the error (or the [manual setup](#manual-setup)). The engine checks them on every run, even when nothing else would change and even when `ruleset.enforcement` is `disabled`, because a ruleset that GitHub could not run would block every pull request in the organization.
- **The run stops with `no team must approve changes to .github/workflows/**`:** add a `requiredReviewers` entry with `minimum_approvals` of at least 1 and `.github/workflows/**` among its `file_patterns`, or an exception on `ruleset.rules.pullRequest.requiredReviewers` with a reason and a date.
- **A pull request waits for "Organization checks":** the ruleset requires the central workflow, and it did not run or has not finished. Open the pull request's checks; if nothing started, check that the `.github` repository still shares its workflows with the organization (Settings → Actions → General → Access) and that `ruleset.rules.workflows[].sha` still names a commit that holds the file (a run of the engine fails otherwise). A repository's first push to a new branch is not blocked: the rule does not apply on creation.
- **A merge is blocked by the ruleset:** read the reason on the pull request. Approvals of another person are required (the last push cannot be approved by its author), review threads must be resolved, changes to workflows, actions, `CODEOWNERS` and Dependabot config need the reviewer team, and only a merge commit is allowed. The organization admin can use *Merge without waiting for requirements to be met (bypass rules)*; GitHub records it on the ruleset's insights page. Do that only for your own pull request when nobody else can approve; a direct push is rejected for everyone.
- **A pull request gets no Copilot review:** check that its author has a Copilot seat and that the AI credits budget is not used up (*Organization settings → Copilot*); request a review by hand from the *Reviewers* menu.
- **The run stops on a `selected_users` request with HTTP 422:** a login of `copilotSeats.selected_usernames` is not a member of the organization, or is misspelled; invite the member first, or correct the login. The actions before it were applied, so re-run after the fix.
- **A workflow fails because an action is not allowed:** add it to `actions.selected.patterns_allowed` and re-run the engine.
- **A workflow fails because an action is not pinned to a full-length commit SHA:** replace the tag with the commit SHA (see [Requirements](#requirements)).
