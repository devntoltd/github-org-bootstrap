# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

PowerShell tool that keeps the settings of a GitHub organization in line with a config file: it reads the
organization, plans the difference, asks once and applies. The engine is in `engine/` (`bootstrap.ps1`,
`GitHubOrg.psm1`, `src/`, `tests/`, `examples/`), shared helpers in `shared/`, developer scripts in `tools/`.
Organizations keep their config in their own repository and run a pinned release with `engine/examples/run.ps1`.
How the code is put together: `docs/architecture.md`. Decisions live in `docs/decisions/` (index with what superseded
each: its `README.md`). User docs: the root `README.md` and `engine/README.md`; see the documentation rules in
`CONTRIBUTING.md`.

## Commands

Requirements (run everything from the repo root):

- PowerShell 7.6 (`pwsh`), the minimum `engine/bootstrap.ps1` requires.
- Runtime modules: none. `modules.lock.psd1` stays empty (`@{}`) because the dev tools read it. The GitHub REST API version `Invoke-GhApi` pins (`$script:GitHubApiVersion`) is raised only after verifying the response shapes (CONTRIBUTING.md). Latest Gallery versions are looked up with `Find-PSResource` of the PSResourceGet in `$PSHOME` (imported by path, never the newest installed one), not `Find-Module`, which leaks `-WhatIf` into its module load.
- Dev tools: root `dev-tools.psd1`, exact versions: `Modules` (Pester, PSScriptAnalyzer; `tools/Invoke-Coverage.ps1` and `tools/Invoke-Lint.ps1` import exactly these through `tools/DevModule.ps1`) and `Tools` (actionlint, shellcheck, zizmor, Betterleaks, lychee, editorconfig-checker: the versions `ci.yml` pins, `tools/tests/Install-DevTools.Tests.ps1` checks it, and the GitHub `Repository` of each). Never read by the engine. `./tools/Install-DevTools.ps1` checks the Gallery dependencies of every locked module, installs the exact versions (`-ModulesOnly` in CI), enables `.githooks` and points `blame.ignoreRevsFile` at `.git-blame-ignore-revs` (commits that only reformat code). `recurring.yml` reports newer versions weekly (`tools/Find-DependencyUpdate.ps1`, then `tools/Invoke-DependencyUpdateCheck.ps1` keeps one issue).
- CI (`.github/workflows/ci.yml`) runs lint (formatting rules included) and tests on Ubuntu, so paths are case-sensitive there, plus editorconfig-checker, shellcheck on the hook, a lychee check of the links between the docs, actionlint, zizmor and a Betterleaks scan of the full history; workflow rules (`persist-credentials: false`, SHA pins, allowed actions) are in CONTRIBUTING.md.

```powershell
# Every check of CI in a row with a summary (non-zero exit on a failure); ./build.ps1 <name> for one, ./build.ps1 for the menu
./build.ps1 all

# All tests
pwsh -NoProfile -Command "Invoke-Pester -Path . -Output Detailed"

# One Describe/It (wildcards on the full test name)
pwsh -NoProfile -Command "Invoke-Pester -Path ./engine/tests/Plan.Tests.ps1 -FullNameFilter 'Get-GitHubOrgPlan*' -Output Detailed"

# Tests with code coverage (what CI runs): per-file table, coverage.xml; fails below -Target (95%)
./tools/Invoke-Coverage.ps1

# Lint: every analyzer rule, one per call (a single call races, PSScriptAnalyzer#1867); must produce no output
./tools/Invoke-Lint.ps1

# Run the engine (offline check, then a dry run; never against an organization without the user asking)
./engine/bootstrap.ps1 -ConfigPath ./engine/examples/github.json -ValidateOnly

# Regenerate engine/github.schema.json after changing a shape (tests fail while it is stale)
./tools/Build-ConfigSchema.ps1

# Regenerate engine/settings.md after changing a row, a settings page or api-endpoints.psd1 (a test fails while it is stale)
./tools/Build-SettingReference.ps1
```

`Invoke-Pester` does not set a failing exit code by default; for a pass/fail exit code use
`$c = New-PesterConfiguration; $c.Run.Path = '.'; $c.Run.Exit = $true; Invoke-Pester -Configuration $c`.

## Architecture

Read [docs/architecture.md](docs/architecture.md) first: the pipeline a run goes through, the file and function of each step, the shared helpers, config shapes, the state and actions (contracts: keep them stable, tests and config repositories rely on them) and the test doubles. Below is only what an agent needs on top of it.

Entry points:

- `build.ps1`: checks are commands run from the root whose output is never captured (results go through a `[ref]`, so a terminal keeps their colors; a check that throws fails alone); tools are scripts run with `Parameters` splatted by name (`-WhatIf` for the ones that write to GitHub). `./build.ps1 all` runs every check without stopping and exits non-zero after a summary. `tests/Build.Tests.ps1` checks `build.psd1` against `ci.yml`, `tools/`, `dev-tools.psd1` and `.vscode/tasks.json`.
- `engine/examples/run.ps1`: the wrapper a config repository copies; `engine.psd1` pins `{Repository; Tag; Commit}`, the tag must point at the commit, `.engine/` is reused at that commit and replaced otherwise; tested with git mocked in `engine/tests/RunWrapper.Tests.ps1`.

The engine:

- the engine: `$script:SettingDefinitions` rows hold section, GitHub field name, type, allowed values, mode `apply`/`check`/`manual`, the settings page (`Page`, a path of `$script:SettingPages` in `src/Config.Catalog.ps1`), and optionally `Nullable`, `Pattern`, `Rule`, `Description`, `Recommended` with `Why` or else `NoRecommendation` (`Project data: ...` or `Owner decides: ...`, a test requires one of the two), `UiGroup`, `UiLabel`, `Hint`, `Options`, `NoUi`, `Read`/`Write` (default to the section endpoint for a row of `$script:Sections`: `Get-SettingRead`, `Get-SettingWrite`), `Docs`, `PlanRestriction`, `ReadRequiresPlan`, `Absent`, `AbsentValue`, `DependsOn` (a boolean field of the section; while the config sets it `false` the plan leaves the row alone and a PUT sends GitHub's value), `Sensitive` (`Read.Field` may be dotted, `a.b`; every key is in `$script:SettingRowKeys`, a test rejects any other); the top-level sections in `$script:TopLevelSections`, a section by subject appears with its first row; no page of `$script:SettingPages` is `pending`, a `manual` row has `Page`, `UiGroup` and `Why`; `$script:Sections` maps section → endpoint path, action, method, state property, label, `Nullable`, in action order; the sections validation walks (`$script:ConfigSections`) come from the rows, so a section exists only through a row. A new setting is a row plus tests and a regenerated schema. `Invoke-GitHubOrgBootstrap` computes `Get-RecommendationReport` once, prints its warnings before those of `Get-GitHubOrgWarning` and its exceptions in force after them, then the line of `Get-ManualSummary` and, with `-ManualChecklist`, the lines of `Get-ManualChecklist`, and with `-PageWalk` the walk of `Get-SettingPageWalk` (`src/Plan.Page.ps1`; `Invoke-SettingPageWalk` in `GitHubOrg.psm1` prints it, opens and stops at each page that needs a person; Enter records nothing), all before the confirmation. `Get-GitHubOrgWarning` is the text of `Get-GitHubOrgWarningItem`, whose items carry the settings page and row of each warning. The state ends with `ReadAt` (UTC). A page of `$script:SettingPages` with rows outside an area has `Order` (its rows top to bottom, `Get-PageRow`) and `ReviewedOn`; every row with such a page has `UiGroup` and a `UiLabel` or `Options`, `<organization>` in UI words standing for the organization (tests in `tests/Config.Catalog.Tests.ps1`). `actions.selected` is `null` unless `allowed_actions` is `selected`; `SelectedActions` is not read then (GitHub would answer 409), and a 409 otherwise is an error. The context check also probes `admin:org_hook`; `$script:ScopeCommand` (`src/State.ps1`) is the one scope hint, `$script:ScopeRemoveCommand` the command `Write-ScopeRemoveRecommendation` prints, in the `finally` and from the context check when only the `admin:org_hook` probe fails.
- The engine: endpoint catalog: `engine/api-endpoints.psd1` (`$script:ApiCatalog`, loaded by `src/Config.Catalog.ps1`; `ApiVersion` equals `$script:GitHubApiVersion`) lists every operation under `/orgs/{org}` and `/organizations/{org}` of the OpenAPI description of the pinned version, and every other one the engine calls, as path → `Category` and method → `Status` `read`/`write`/`unused` (with `Reason`). `Fields` (on the GETs of the `$script:Sections` endpoints and of every endpoint a row reads, `copilot/billing` included) names the response fields no row reads, with the reason; any other field of such an answer is a warning (`Get-UnknownResponseField`, after the not-observed warnings). `Body` (every `write` PUT/PATCH) lists the request body fields of the description: a PUT section sends exactly them. A new call of the engine, a new row or a raised API version updates the file in the same change; `tests/Config.Catalog.Tests.ps1` checks it against the gh calls of round trip scenarios on the fake.
- The engine: files by area: the settings and the pipeline entry points in `src/Config.ps1`, `State.ps1`, `Plan.ps1`; inventory in `src/Config.Inventory.ps1`, `State.Inventory.ps1`, `Plan.Inventory.ps1`; budgets in `src/Config.Budget.ps1`, `State.Budget.ps1`, `Plan.Budget.ps1`; Copilot seats in `src/Config.CopilotSeat.ps1`, `State.CopilotSeat.ps1`, `Plan.CopilotSeat.ps1`; code security in `src/State.CodeSecurity.ps1`, `Plan.CodeSecurity.ps1` and the organization ruleset in `src/State.Ruleset.ps1`, `Plan.Ruleset.ps1` (their config fields are rows of `$script:SettingDefinitions`). Helpers that more than one area uses (`Read-OrgEndpoint`, `ConvertTo-FieldMap`, `Read-OrgRepository`, `Get-ConfiguredValue`, `Get-NameSet`, `Compare-NameSet`, `Format-SettingValue`) stay in the settings files; each area file has its `tests/<File>.Tests.ps1`.
- The engine: inventory and code security fields: `Owners` (logins), `Apps` (`{Slug, RepositorySelection, Permissions}`), `Webhooks` (`{Host, Url, Events, Active, Https, VerifiesTls, HasSecret}`; `Url` is only `scheme://host/...` since the path can be a secret, `Host` is punycode, `VerifiesTls` is `$null` when GitHub does not say, the secret is never kept), `OutsideCollaborators` (logins), `Invitations` (`{Login, Email, Role, Inviter, CreatedAt}`, `yyyy-MM-dd` UTC, `Login` or `Email` may be `$null`), `RepositoryInvitations` (`{Repository, Login, Permission, Inviter, CreatedAt, Expired}`, every repository, archived ones included, `Login` may be `$null`), `SkippedRepositories` (the repositories whose invitations answered 404, a warning). `CodeSecurity`: `Configuration` is `{Id, Name, Description, Enforcement, Settings}` or `$null`; `OtherDefaults` `{Name, DefaultForNewRepos}`; `Repositories` `{Name, ConfigurationId, ConfigurationName, Status}`. The repository list is read once for both (code security leaves archived ones out); repositories come from the list of each organization and global configuration (`orgs/{org}/code-security/configurations/{id}/repositories`), and only those no list answers (none, an enterprise configuration, `detached`) get a read of their own, where a 404 skips the repository into `SkippedRepositories` (a warning). For a configuration created in the same run, the endpoints of the later code security actions carry `{configuration_id}`, which `Invoke-GitHubOrgPlan` fills from the create response; `AttachCodeSecurityConfiguration` uses `all_without_configurations`.
- The engine: Copilot seats: state `CopilotSeats` is `{PlanType, SeatManagement, Total, Seats, Teams}` (`Seats` `{Login, Team, PendingCancellation}`, `Teams` slug -> logins of each team of the config or `$null`), `$null` on a 404 of `copilot/billing` or on seat management `unconfigured` (an organization that never bought Copilot gets 200); `copilot/billing` is read once (`Read-CopilotBilling`, before the check-only endpoints; an answer that is not an object stops the run, only a 404 means no plan), and the seats, the ruleset's plan and the checked Copilot policies take it from there; without a plan, rows with `Absent = 'CopilotPlan'` are not applicable and their endpoints are not read. GitHub lists seats, not the teams it was given, so a team compares through its members. Actions `AddCopilotSeats` and `AddCopilotTeam` (POST, after the budgets) only while seat management is `assign_selected`, since GitHub answers 422 otherwise; a seat outside the config is a warning.
- The engine: ruleset: state `Ruleset` is `{Current, OtherRulesets, Teams, WorkflowSources, RepositoryVisibilities, References, Copilot}` (`Current` is the organization ruleset of the exact name as GitHub returns it, `$null` when none; `Teams` slug → `{Id, Slug, HasRepositoryWrite}` or `$null`; `WorkflowSources` `"<repository>/<path>@<sha>"` → `{RepositoryId, Visibility, AccessLevel, Content}`; `References` file name → text of the file of that name beside the config (`Get-GitHubOrgState -ConfigDirectory`), a workflow without one is not compared; `Copilot` `{PlanType, Seats}` from state `CopilotSeats`, `$null` without a plan or while `ruleset.rules.copilotCodeReview.enabled` is `false`; without a plan or seat only a warning). Actions `CreateRuleset` (POST) or `UpdateRuleset` (PUT, the whole body from `Get-RulesetBody`), after the code security actions; the target is fixed in the code (branch, every repository, the default branch). The plan throws (`Assert-RulesetPrecondition`) when a central workflow cannot run (repository or file missing, Actions access not shared, visibility too narrow), also when `enforcement` is `disabled`, and plans nothing while a reviewer team does not exist (a warning). `Get-WorkflowReviewerReport` (`src/Config.ps1`) requires a `requiredReviewers` entry that covers `.github/workflows/**` and is not waived by an exception on `ruleset.rules.pullRequest.requiredReviewers`; the shape key `RuleExceptions` marks a field whose engine rule takes exceptions (`Get-RuleExceptionReport`, `shared/src/ConfigShape.ps1`), `Maximum` caps an integer. Bypass actors compare by `actor_type` and `bypass_mode` (GitHub ignores `actor_id` for `OrganizationAdmin`/`DeployKey`). `engine/org-checks.yml` is the reference copy of the central workflow, compared ignoring line endings with the one at the configured `sha` (a warning); `Invoke-GhApi` sends bodies as JSON of depth 10. `.github/CODEOWNERS` is project data.

Shared code and shapes:

- `shared/Bootstrap.Common.psm1` keeps only `$script:GitHubApiVersion` (read by path from `tools/`), `$script:VersionRowFormat`, the dot-sources and the exports; the functions are in `shared/src/` by area: `Config.ps1`, `ConfigShape.ps1`, `Output.ps1`, `GitHub.ps1`, each tested in `shared/tests/<File>.Tests.ps1`.
- `Get-ConfigPattern` holds the shared patterns (GUID, GitHub login and others). An array marked `Unique` rejects repeated items, or repeated values of its `ItemKey`, case-insensitively; one marked `ItemExceptions` takes exceptions for its items as `<list>['<item>']`, applied through `Get-ItemExceptionReport`. A new shape node key goes into `$script:ShapeNodeKeys`.
- `Invoke-GhApi -Paginate` reads every page through `gh api --paginate --slurp`; `-NoEnumerate` returns the JSON root as it is (an array stays an array, also with one item), which the section and check-only reads of the engine use for the observations. A failed call throws an `HttpRequestException` whose `StatusCode` is gh's `HTTP nnn`, or the `status` of the error body when gh prints no code, or `$null` without an answer; callers check it with `Test-GhStatus`, never the message, and a wrapper with its own message that a status check sits behind passes the original as the inner exception (`Read-OrgEndpoint`; the context checks throw plain strings).
- `tools/Invoke-RecurringReminder.ps1` (weekly in `recurring.yml`) opens reminder issues from `.github/ISSUE_TEMPLATE/recurring-*.md` (label `recurring`), intervals in `.github/recurring-operations.psd1`, history matched by the label `recurring:<operation>`, never by title. `tools/Invoke-GitHubApiVersionCheck.ps1` opens an issue from `github-api-version.md` (label `github-api-version`, the version marked in its body) when GitHub supports a REST API version newer than `$script:GitHubApiVersion`. `tools/Invoke-DependencyUpdateCheck.ps1` keeps one issue for the dependency updates (label `dependency-update`, a marker per candidate). `tools/Invoke-ApiEndpointCheck.ps1` (`./build.ps1 endpoints`) downloads the OpenAPI description of the pinned version (or `-Version`) and opens one issue per difference from `engine/api-endpoints.psd1` (template `api-endpoint.md`, label `api-endpoint`, markers `<!-- api-endpoint: <METHOD> <path> -->` and `<!-- api-endpoint-difference: <signature> -->`; none while an issue of the operation is open, one by hand without the second marker covers the operation): a new operation under `/orgs/{org}` or `/organizations/{org}`, a listed one no longer described, a `Body` difference of a `write` PUT or PATCH (a body that is not JSON or has `oneOf`/`anyOf` is only reported); it gathers and sanity-checks everything (JSON with `paths`, every `$ref` resolved, an `/orgs/{org}` operation, at least 90% and at most 10 missing of the listed operations, the issue list) before it writes. `-Report` opens nothing and also prints the response fields of `read` GETs with `Fields` that neither a row (`Get-GitHubOrgReadField`, the one engine function it imports) nor `Fields` lists: never an issue. All four dot-source `tools/GitHubIssue.ps1`: `Invoke-Gh`, `Read-IssueTemplate`, `Assert-IssueTemplate` (title and matching label), `Get-LabeledIssue` (throws when the list reaches its limit), `Find-IssueByMarker`, `Add-MissingLabel` (labels read once per run), `New-IssueFromTemplate` (creates the missing labels first; `ShouldProcess` is its own), `Add-StepSummary`, and `Get-PinnedGitHubApiVersion`, which `tools/Find-DependencyUpdate.ps1` also uses; they are tested in `tools/tests/GitHubIssue.Tests.ps1`.

Tests:

- Each `.psm1` exports only its public functions through the `Export-ModuleMember` line at the bottom: add new public functions there; private helpers are tested through public ones. Mocks of cmdlets called from shared code use `-ModuleName Bootstrap.Common`, including `Write-Progress` for the progress helpers.
- gh stub details: `--header` pairs are recorded apart, in `Headers`; a list response from `Get-TestGhPagesResponse` / `Get-TestGhObjectPagesResponse` answers only a call with `--paginate`; the fake API's GET reads the store, PUT replaces, PATCH merges, handlers do the rest (`Register-TestGitHubOrgFake` in `engine/tests/TestData.ps1`). The native fake gh is a shell script on Linux and a launcher exe built with the `csc.exe` of .NET Framework on Windows; it also runs the smoke test of `engine/bootstrap.ps1`. `Add-TestModule` exists because a mock of `Get-Module` cannot show how modules load.
- Helpers: `Get-PlanAction` and `Get-PlanIndex` (`shared/tests/PlanIndex.ps1`) give an action of a plan (`$null` when missing) and its position; `Assert-ConfigError` (`shared/tests/ConfigError.ps1`) checks the config error of one path by its parts; `Get-GhCall` and `Get-GhOption` (`tools/tests/GhMock.ps1`) read the gh calls of the `tools/` tests.
